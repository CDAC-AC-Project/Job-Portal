1. AUTH_USER-SERVICE
====================================================================

What exists (and works, in isolation):
  - POST /auth/register — validates via RegisterDto (@NotBlank/@Email/
    @NotNull role), rejects duplicate email, BCrypt-hashes the
    password, saves the User, returns a signed JWT + user info.
  - POST /auth/login — verifies password with BCryptPasswordEncoder,
    checks `active` flag, returns a JWT.
  - JwtServiceImpl issues HS256 tokens with claims: userId, role,
    subject=email, issuer="Auth_User-Service", 24h expiry
    (jwt.expiration=86400000ms).
  - User entity: id, fullName, email (unique), password, role
    (CANDIDATE/RECRUITER/ADMIN), emailVerified, active.
  - Runs on port 8083, registers with Eureka as "AUTH-SERVICE"
    (spring.application.name: AUTH-SERVICE).

Gaps / missing pieces:
  - Endpoints referenced by its own SecurityConfig permitAll list —
    "/auth/verify-email", "/auth/forgot-password", "/auth/reset-password"
    — DO NOT EXIST in AuthController. Only /register and /login are
    implemented. Email verification and password reset are stubbed
    in config but never built.
  - No "change password" endpoint. The frontend's
    RecruiterAccountSettings.jsx literally has a comment: "Password
    changes are handled by the Auth Service, which isn't wired up
    yet" — confirming this from the other side.
  - No "get current user / me" endpoint, no refresh-token endpoint,
    no logout endpoint (logout is entirely client-side today —
    authStorage.js just clears localStorage).
  - No CORS configuration anywhere in this service. SecurityConfig
    calls `.cors(cors -> {})` (an empty customizer) but there is no
    `CorsConfigurationSource` bean anywhere in the service. This is
    the exact same class of bug we found (and fixed) in the standalone
    Profile Service earlier — if a browser ever called this service
    directly, most requests would be blocked by CORS.
  - Registers with Eureka under the name AUTH-SERVICE, but the API
    Gateway's route table (see section 3) looks up AUTH-USER-SERVICE.
    These do not match — Eureka-based routing to this service will
    fail even once everything else is fixed, unless one of the two
    names is corrected.
  - jwt.secret is read from environment variable JWT_SECRET
    (`${JWT_SECRET}` in application.yml). There is no .env file or
    documented value anywhere in the repo — whoever runs this service
    must already know to set JWT_SECRET, and the exact same value
    must also reach the API Gateway (see section 3) for token
    validation to succeed. Nothing currently guarantees that.
  - Frontend integration: NONE. authStorage.js never calls this
    service. It derives a fake numeric "userId" from
    hash(role + ":" + email) purely on the client and uses that to
    bootstrap a Profile Service record. There is no real
    authentication, no real password check, and no session tied to
    this service anywhere in the current app.
  - Port conflict with Jobs-service (see section 4 / section 0).

3. API GATEWAY
====================================================================

What exists:
  - Spring Cloud Gateway (MVC/blocking variant —
    spring-cloud-starter-gateway-server-webmvc, not the reactive one),
    port 8080, registers with Eureka as API-GATEWAY.
  - Route table (application.yaml) forwards by path prefix to
    Eureka-discovered services:
      /auth/**          -> lb://AUTH-USER-SERVICE
      /profiles/**      -> lb://PROFILE-SERVICE
      /jobs/**          -> lb://JOB-SERVICE
      /applications/**  -> lb://APPLICATION-SERVICE
      /notifications/** -> lb://NOTIFICATION-SERVICE
  - JwtAuthenticationFilter: reads Authorization: Bearer <token>,
    validates via JwtUtil, strips any client-supplied
    X-User-Id/X-User-Email/X-User-Role headers and replaces them with
    trusted ones derived from the validated token before forwarding
    downstream. This is a reasonable, secure pattern in principle.
  - A CorsConfigurationSource bean IS correctly defined here
    (allows http://localhost:5173, standard methods, Authorization +
    Content-Type headers, credentials on). This part is done right.

Gaps / bugs found:
  - Route/registration name mismatch: the route table expects
    "AUTH-USER-SERVICE" in Eureka, but Auth_User-Service registers
    itself as "AUTH-SERVICE" (spring.application.name). As configured
    today, the gateway's /auth/** route can never find a live
    instance. Same risk applies to PROFILE-SERVICE once/if the real
    profile service is ever registered — its name must exactly match
    "PROFILE-SERVICE".
  - SecurityConfig is unrelated boilerplate that doesn't match this
    project:
      .requestMatchers("/login").permitAll()
      .requestMatchers("/register").permitAll()
      .requestMatchers("/actuator/health").permitAll()
      .requestMatchers(GET, "/products/**").hasAnyRole("CUSTOMER","ADMIN")
      .requestMatchers(POST, "/products/**").hasRole("ADMIN")
      .anyRequest().authenticated()
    None of this project's real routes are "/login", "/register" (they
    are "/auth/login", "/auth/register" once past the gateway), or
    "/products/**". There is no "CUSTOMER" role anywhere in this
    system (Role enum is CANDIDATE/RECRUITER/ADMIN). Practical effect:
    every real route in this project — including /auth/register and
    /auth/login themselves — falls through to
    `.anyRequest().authenticated()`, which means the gateway will
    demand a valid JWT to even reach the registration/login endpoints.
    That's a hard deadlock: you cannot get a token without first
    having a token. This must be rewritten to permitAll on
    "/auth/register" and "/auth/login" (and probably GET /jobs/** for
    public browsing) and to use the real roles for anything that
    should be protected.
  - jwt.secret is never defined in ApiGateway's application.yaml
    (no jwt: block at all, not even an env-var placeholder), yet
    JwtUtil requires `@Value("${jwt.secret}")`. As configured, the
    gateway will fail to start (missing required property) unless
    jwt.secret is injected from outside the repo (e.g. an IDE run
    config or OS env var) — and there's nothing in the repo enforcing
    that this externally-supplied value is identical to Auth
    Service's JWT_SECRET. If they ever differ, every token the
    gateway sees will fail validation.
  - No route exists at all for the Profile-Service's real API shape.
    Even ignoring the "which Profile-Service" question above, the
    route predicate is `Path=/profiles/**` while the actual working
    service exposes `/api/profile/**` — a rewrite filter would be
    needed either way.
  - Port collision with the standalone (real) Profile_service, both
    claiming 8080 (see section 0/2).
  - Nothing in the frontend currently sends traffic to port 8080's
    gateway routes in the shape the gateway expects — the frontend
    bypasses the gateway entirely for every service it talks to
    today. The Gateway + JWT filter, however correctly built in
    isolation, is not currently exercised by the running application.

4. EUREKA / SERVICE REGISTRY
====================================================================

What exists:
  - A minimal, correct Eureka server: @EnableEurekaServer, port 8761,
    register-with-eureka: false, fetch-registry: false (standard,
    correct settings for a standalone registry). Nothing to fix here
    — this piece is fine as far as it goes.
  - spring-cloud-starter-netflix-eureka-client is present in every
    Java service's pom.xml (Auth_User-Service, Jobs-service,
    Application-service, and even the empty Profile-Service stub), so
    the dependency wiring for clients is consistent.
  - Auth_User-Service and Jobs-service both explicitly configure
    eureka.client.service-url.defaultZone: http://localhost:8761/eureka
    with register-with-eureka/fetch-registry: true — these two are
    correctly set up to join the registry.

Gaps:
  - Application-service has its Eureka block commented out entirely
    ("# Eureka (Enable later if you're using Eureca)" /
    "# eureka.client.service-url.defaultZone=..."). It will not
    register with Eureka as currently configured, even though its
    pom.xml has the client dependency and it has a JobClient class
    that appears intended to call Jobs-service (likely expecting
    discovery to resolve JOB-SERVICE) — so this is very likely a
    forgotten "uncomment before running" step rather than an
    intentional decision.
  - Profile-Service (the empty stub, section 2) has no Eureka config
    block at all — nothing to register even once code is added,
    until someone adds eureka.client.service-url.defaultZone.
  - NotificationService is written in C#/.NET (ASP.NET Core —
    Program.cs, NotificationController.cs, appsettings.json, EF Core
    migrations), not Java. There is no Eureka client wiring possible
    the same way the other services do it (no Steeltoe discovery
    client or equivalent found). As configured, the Gateway's
    lb://NOTIFICATION-SERVICE route can never resolve — that service
    is architecturally unable to join this Eureka registry without
    additional work (a .NET Eureka/Steeltoe client, or dropping
    service discovery for it and hardcoding its URL in the gateway
    instead).
  - Net effect: of the 5 gateway routes, only 2 services
    (Auth_User-Service under the "wrong" name, and Jobs-service) are
    actually configured to register with Eureka today.
    Profile-Service (empty), Application-service (commented out), and
    NotificationService (wrong tech stack) will not appear in the
    registry as things stand.
